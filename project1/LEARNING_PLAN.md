# План перехода .NET → Go

Контекст: пишете API, консольные утилиты и автономные сервисы по расписанию на .NET.
Про Go — синтаксис, тулинг, отладку, экосистему — пока не знаете вообще. Цель плана —
довести до уровня "уверенно пишу и отлаживаю сервисы на Go", используя ваш опыт
.NET как ускоритель (везде, где это возможно, буду проводить параллели с C#/.NET).

Формат работы: план разбит на этапы с мини-задачами. После каждого этапа — жду от вас
результата (кода или ответов на контрольные вопросы), проверяю, объясняю, что было не так,
и даём добро на следующий этап. Темп подстраиваем под вас — если что-то идёт быстро,
пропускаем очевидное; если тема не заходит — останавливаемся и разбираем подробнее.

## Ключевая разница в философии (прочитать один раз, держать в голове)

| .NET | Go |
|---|---|
| CLR, JIT, сборка мусора с поколениями | компилируется в нативный бинарник, GC проще, но есть |
| ООП: классы, наследование, `virtual`/`override` | нет классов и наследования вообще — только структуры + композиция + интерфейсы |
| Интерфейсы реализуются явно (`class Foo : IBar`) | интерфейсы реализуются **неявно** (structural typing, как duck typing, но с проверкой компилятором) |
| Исключения (`try/catch`, `throw`) | исключений почти нет — ошибки это **значения**, возвращаются вторым return-параметром |
| `async`/`await`, `Task`, `Task.WhenAll` | горутины (`go func()`) + каналы (`chan`), планировщик рантайма сам мультиплексирует горутины на потоки ОС |
| NuGet + `.csproj` | Go modules + `go.mod`/`go.sum` |
| `IDisposable` + `using` | `defer` |
| Generics (давно есть) | Generics есть, но появились только в Go 1.18 (2022) — код в экосистеме местами их избегает |
| Богатая стандартная библиотека + куча фреймворков (ASP.NET Core, EF Core) | стандартная библиотека уже покрывает HTTP-сервер, роутер тонкий (chi/gin), ORM обычно не используют — пишут SQL руками (pgx/sqlx) |
| Rider/VS + встроенный отладчик | GoLand/VSCode + Delve — тот же уровень удобства, ничего не теряете |

Самое непривычное для вас будет: **отсутствие исключений** и **отсутствие классов**.
Это не баги, а осознанный дизайн — Go специально минималистичный.

## Этап 0 — Инструменты и первый прогон (0.5 дня)

Цель: пощупать `go run`, `go build`, `go test`, отладчик в GoLand — на примере, где всё уже понятно.

- Аналогии команд:
  - `dotnet run` → `go run main.go`
  - `dotnet build` → `go build`
  - `dotnet test` → `go test ./...`
  - `dotnet restore` → `go mod download` / `go mod tidy`
  - `dotnet format` / Roslyn analyzers → `gofmt`, `go vet`, `golangci-lint`
- Задание: написать `hello.go` (просто `func main()` с `fmt.Println`), запустить через `go run`,
  поставить breakpoint в GoLand, запустить в режиме Debug, убедиться что step over/into работают
  так же, как в Rider.
- Контрольный вопрос: чем `go run` отличается от `go build && ./binary`?

## Этап 1 — Синтаксис и типы (3–5 дней)

Цель: читать и писать простой Go-код без страха.

Темы:
- Пакеты и `import` (аналог namespace, но пакет = папка, имя пакета = экспорт через **заглавную букву**
  идентификатора, а не `public`/`private`)
- Переменные: `var`, `:=`, zero values (в Go нет `null` для примитивов и структур — есть нулевые значения)
- Базовые типы, слайсы (`[]T`, аналог `List<T>`, но с нюансами по capacity/append), массивы, мапы (`map[K]V`)
- Структуры (`struct`) — замена классам, без наследования
- Методы на структурах (`func (s *Server) Start()`) — value receiver vs pointer receiver, это как
  "передавать по значению vs по ссылке", важно понять разницу с C#-классами (которые всегда by-reference)
- Интерфейсы — неявная реализация, маленькие интерфейсы (`io.Reader` — один метод) — это **очень**
  идиоматичный Go, непохоже на C#-привычку делать большие интерфейсы
- Обработка ошибок: `if err != nil { return err }`, `errors.New`, `fmt.Errorf("...: %w", err)`
  (аналог `throw new Exception("...", innerException)`, но без stack unwinding)
- `defer` — аналог `using`/`finally`, но выполняется в конце функции, не блока
- Указатели (`*T`, `&x`) — это не C# `ref`/`out`, но близко по духу; поймёте быстро

Практика: небольшая консольная утилита — например, читает CSV или JSON файл, парсит,
считает агрегаты, пишет результат в файл. Знакомая вам по .NET задача, но на Go.

Ресурсы:
- [A Tour of Go](https://go.dev/tour/) — интерактивно, 2-3 часа, обязательно пройти целиком
- [Effective Go](https://go.dev/doc/effective_go) — читать после Tour, как "best practices" документ

## Этап 2 — Конкурентность (5–7 дней)

Это главное, что стоит выучить хорошо — именно тут Go сильно отличается от `async/await`.

Темы:
- Горутины (`go f()`) — легковесные, рантайм сам их шедулит на OS-потоки (M:N модель).
  В отличие от `Task` в .NET, горутина — это не обёртка над thread pool заданием, а
  самостоятельный "зелёный поток" со своим стеком
- Каналы (`chan T`) — способ горутинам общаться и синхронизироваться (аналогов в BCL нет,
  ближе всего `System.Threading.Channels`, но в Go это часть языка, а не библиотека)
- `select` — мультиплексирование каналов (аналог `Task.WhenAny`, но встроен в язык)
- `context.Context` — это прямой аналог `CancellationToken`, только шире: несёт ещё и deadline,
  и request-scoped values. Используется буквально везде, где в .NET вы бы прокидывали `CancellationToken`
- `sync.WaitGroup` (аналог `Task.WhenAll`/`CountdownEvent`), `sync.Mutex` (аналог `lock`),
  `sync.Once` (аналог `Lazy<T>`)
- Data race detector: `go test -race` / `go run -race` — бесценно, ловит гонки на лету

Практика: воркер, который параллельно обрабатывает N задач с ограничением конкурентности
(worker pool), умеет останавливаться по `context.Context` (аналог graceful shutdown по
`CancellationToken` в вашем хостовом сервисе), и пишет результаты в канал.

## Этап 3 — Тулинг и экосистема (3–5 дней)

Темы:
- Go modules подробно: `go.mod`, `go.sum`, semver, `go mod tidy` (аналог `PackageReference` + restore)
- Тестирование: `go test`, табличные тесты (`t.Run` в цикле — идиома вместо `[Theory]`/`[InlineData]`
  из xUnit), `testify` (`assert`/`require` — почти 1-в-1 FluentAssertions), моки через `mockgen`
  (аналог Moq)
- Веб-фреймворки: в Go нет "тяжёлого" ASP.NET Core — обычно берут тонкий роутер
  (`chi`, `gin`, `echo`) поверх стандартного `net/http`. HTTP-хендлер — это просто функция
  `func(w http.ResponseWriter, r *http.Request)`, никакой magic DI-контейнер из коробки
- Конфигурация: `cleanenv`/`viper` (аналог `IOptions<T>` + `appsettings.json`)
- Работа с БД: чаще без ORM — `pgx`/`sqlx` + руками написанный SQL, либо кодогенерация
  (`sqlc`, `xo`) вместо EF Core migrations
- gRPC: `google.golang.org/grpc` + `protoc`/`buf` — если знаком gRPC в .NET, тут почти
  всё то же самое на уровне идей

Хорошая новость: у вас **уже есть репозиторий с реальным продакшн-стеком** — папка
`services/task-service` в этом же репо использует `chi`, `grpc-gateway`, `pgx`, `sarama`
(Kafka), `cleanenv`, `goose` (миграции). Это ровно тот стек, который стоит выучить. После
этого этапа советую открыть [services/task-service/internal/app.go](services/task-service/internal/app.go)
и [services/task-service/cmd/main.go](services/task-service/cmd/main.go) и просто читать —
уже должно быть понятно процентов 70.

## Этап 4 — Идиомы и структура проекта (2–3 дня)

Темы:
- Типичная раскладка Go-проекта: `cmd/`, `internal/`, `pkg/` — зачем `internal`
  (компилятор физически не даёт импортировать его снаружи модуля — это встроенный
  аналог `internal` в C#, только на уровне путей, а не keyword)
- Wrapping ошибок и `errors.Is`/`errors.As` (аналог `catch (SpecificException e)`, но через
  функции, не через типизированный catch)
- Почему в Go мало DI-фреймворков и как обычно собирают зависимости руками в `main`/`init`
  (в противовес `IServiceCollection` в .NET) — конструкторы + explicit wiring
- Линтеры: `golangci-lint` — аналог связки Roslyn analyzers + StyleCop
